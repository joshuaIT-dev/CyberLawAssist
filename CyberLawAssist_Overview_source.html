CyberLawAssist System Overview

System functions, architecture, data, configuration, backup, and operating manuals
Project reference document | 7 November 2026

CyberLawAssist is a local web portal for multilingual cyberlaw information, preparation checklists, office intake and reporting, and support. This document describes the implementation in the project source. The chatbot provides prepared informational guidance and is not a legal decision maker or substitute for advice from a qualified professional.

1. Purpose and scope

The project serves three audiences: guests who use public information and browser-based chat; registered users who have a private workspace and saved services; and administrators who manage accounts, content, office intake, support, notices, and reports. It is designed for a local XAMPP host and can be reached by other devices on the same private network through the host computer's LAN address.

Registration and sign-in

Public registration creates User accounts only and records acceptance of the current Terms and Privacy acknowledgement. Administrators are created by an existing administrator through Users → Create administrator. On a fresh setup, the installer creates a first administrator only if none exists; its random initial credentials are written outside the web root in cyberlawassist-private/first-admin.txt. Change the initial password immediately. User sign-in uses email; admin sign-in supports the unique admin number. Workspace access follows the database role. Log out before switching accounts.

3. System architecture and interfaces

LayerImplementationInterface
ClientHTML pages, CSS, JavaScript, browser storage and service worker.Web browser over HTTP to Apache. Guests can use browser-local chat history. On localhost, selected public static pages can be cached for offline display; private account/API data is excluded.
Web/APIApache with PHP. PHP sessions, JSON API, CSRF checks, role and ownership checks, prepared SQL queries, DOCX export.Browser calls PHP API endpoints. PHP returns JSON and generated Word files.
DatabaseMariaDB 10.4.32 in the current XAMPP installation; InnoDB and utf8mb4.PHP PDO connects to 127.0.0.1:3306 using a restricted app account.
Chat serviceLocal Python retrieval service and prepared Q&A dataset, 3,069 English/Tagalog/Taglish Q&A pairs.PHP proxies requests to http://127.0.0.1:8001/api/chat. Keep Python bound to loopback; client devices need only Apache access.

Chat data flow

  1. Browser submits a chat question to PHP. The public guest AI action is ephemeral; registered chat actions also persist the conversation and message state in MariaDB.
  2. PHP forwards the message, selected language and optional topic context to the local Python service.
  3. Python ranks prepared Q&A content and returns an answer, language, topic, sources and suggestions. It does not call an external AI or learn from conversations.
  4. For registered accounts, PHP stores the assistant response and response metadata. Guest conversation history remains in browser storage.

Other data flows and external interfaces

  • Authentication and protected API calls use PHP sessions and CSRF tokens; account-specific records are checked against the signed-in account.
  • Admin intake forms write case records; report queries summarize database records by week, calendar month or year.
  • Support messages create in-app notifications for the other party; support refreshes about every five seconds. No email or SMS delivery service is configured.
  • Law pages and office contacts are served from MariaDB content tables.
  • Lucide icons use an external CDN when internet is available. The chatbot itself needs no cloud key or internet connection for responses.

4. Software and hardware components

Software: Windows/XAMPP environment; Apache; PHP CLI and web runtime with PDO MySQL, cURL and PharData support; MariaDB 10.4.32; Python 3.10+ (or uv) for the local chatbot; modern browser with JavaScript; local project files. FastAPI/Uvicorn is optional; the launcher can use a built-in Python HTTP server. See README.md and phyton ai/README.md for startup details.

Hardware: a Windows computer hosting Apache, MariaDB and the Python service; client computers/phones/tablets with a modern browser on the same LAN when multi-device access is needed; storage sized for database, source, logs and backups. The repository does not specify minimum CPU, RAM, disk or network throughput; set these from expected use and measured load.

5. Configuration and operations

  • Start MySQL and Apache in XAMPP, then run start-project.bat. Open http://localhost/CyberLawAssist/.
  • For a fresh installation, run the PHP CLI command for database/setup.php as described in README.md. Setup creates/seeds the 12 tables, provisions a restricted app account, migrates as needed, and creates the initial admin only if no admin exists.
  • Private database configuration and PHP sessions are outside htdocs, under cyberlawassist-private. The config contains DSN, app username/password and local AI URL. Do not copy secrets into public web files or source control.
  • The application DB account has SELECT/INSERT/UPDATE/DELETE permissions rather than schema administration. Setup credentials can be supplied through CLA_DB_SETUP_USER and CLA_DB_SETUP_PASSWORD.
  • Run database/migrate.php via PHP CLI after taking a backup when upgrading an existing installation. schema.sql is for fresh installation; do not rerun it blindly on a populated database.
  • Start the local AI service using phyton ai/start-ai.bat or its PowerShell equivalent. Verify the local health endpoint at http://127.0.0.1:8001/api/health.
  • To reach from a phone on the same private Wi-Fi, browse to the host's LAN IP path /CyberLawAssist/. Allow Apache only on the intended private network. Do not expose MariaDB or Python port 8001 to client networks.
  • There is no localhost-to-HTTPS redirect. Use only on a trusted network or put an approved TLS reverse proxy in front before internet-facing deployment.

Foreign keys enforce ownership and related records. Chat messages cascade with their conversation; translations cascade with their topic; support messages cascade with their thread. The schema uses restrictive deletion for user records that may own office records. Backup all 12 tables together to preserve relationships.

7. Backup and recovery

The repository documents manual database backups through XAMPP/phpMyAdmin. It does not configure a scheduled backup job or automatic recovery. Assign an operator to maintain a regular backup schedule appropriate to the office's data loss tolerance.

  1. In phpMyAdmin, select cyberlawassist, choose Export, use a SQL export with structure and data, and save the file to a protected backup location. Alternatively use the MariaDB command-line dump utility with an authorized database administrator account.
  2. Keep encrypted/offline or access-controlled copies separate from the host. Maintain more than one dated copy and periodically test restoration to a separate test database.
  3. Separately protect the private configuration and initial-admin records under cyberlawassist-private. They contain credentials and must never be published. Preserve the project source and Python dataset as a separate software backup.
  4. For recovery, install a compatible XAMPP/MariaDB environment, restore database and protected configuration, restore project files, run applicable migrations only after making a pre-migration backup, then verify sign-in, public pages, registered chat, support, intake and reports.
  5. Guest history lives in browser storage and is not included in the MariaDB export. Browser storage may be lost when cleared or when the browser/device is replaced.

8. User manual

  1. Open the CyberLawAssist home page. Use law information and the chatbot as general information. Check the cited sources and contact appropriate offices for current requirements.
  2. To register, choose Create account, provide the required details, choose a password of at least eight characters, review the Terms and Privacy Policy, and submit. Registration creates a User account.
  3. Sign in with email and password. Use the assigned User workspace. Sign out before another person uses the same browser.
  4. In Chatbot, choose automatic, English, Tagalog or Taglish; ask a clear question. Start a new conversation or use history to reopen, rename, pin or delete saved chats. If the service is unavailable, check that the local Python service is running and retry.
  5. Use Checklist to add and complete preparation steps. Print the checklist or export it as a Word file.
  6. Use Live support to send a message to the office and check back for a reply. Support is for registered Users.
  7. Use Profile/Settings to update contact details, preferences and password. A current password is required for sensitive changes. Password changes invalidate older sessions.
  8. Use Alerts/Notifications to review and mark notices read. Notices are in-app; no email/SMS alert is configured.

9. Administrator manual

  1. On first installation, retrieve the initial admin number/password from the protected first-admin.txt outside htdocs. Sign in through Admin log in, then change the initial password and store credentials securely.
  2. Open the Admin workspace. Review the dashboard and users list. Public registration does not grant admin rights.
  3. Create another administrator through Users → Create administrator. Supply unique admin number and account details. Existing admins are retained.
  4. Manage user accounts: disable access when needed; reset a User password only after verifying identity and entering your own admin password. Permanent deletion requires typing DELETE and the admin password. Deletion is blocked if the account created office case records; disable it instead.
  5. Use Intake/Cases to create or search records, open a record, update factual fields and status, and save. If another admin changes the record concurrently, reopen it and reconcile the latest version before editing.
  6. Use Reports to choose a week, month or year and export a Word report. Verify the selected period before sharing or printing.
  7. Use Live support to select a user's thread and reply. Messages refresh periodically and create an in-app notice for the other party.
  8. Use Notifications/Alerts and law/contact management pages to maintain published content. Check translations, source references, contact details and publication state before saving.
  9. Sign out after administrative work. Disable accounts rather than deleting records that must remain linked for office reporting.

10. Security, limits and maintenance

The implementation includes password hashing, session regeneration, CSRF protection, login attempt controls, role/ownership checks, prepared SQL queries, account session invalidation on password reset/disable, and a restricted database account. These controls do not replace host patching, least-privilege network access, TLS for broader deployments, secure physical access, backup testing and staff privacy procedures.

The chatbot is a prototype corpus of prepared responses using text similarity, not a generative legal expert. Similarity scores are not legal confidence. The project notes that content and translations require authorized legal review before public deployment and that office hours/requirements must be confirmed directly. Do not enter unnecessary sensitive personal information in chats or notes.
